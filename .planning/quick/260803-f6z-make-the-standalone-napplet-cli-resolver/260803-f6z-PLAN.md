<objective>
Make the installed standalone `napplet` executable self-contained for its two package-backed onboarding commands while keeping the maintained packages as the single implementation source.

Purpose: `napplet create` and `napplet skills` currently delegate through a runtime package resolver, so the advertised standalone binary still depends on external Node package-runner availability. Replace that process boundary with import-safe package CLI calls, prove the compiled executable works offline, and preserve the public command contract.

Output: Callable boilerplate/skills entry points, direct CLI imports, Deno workspace/release-build wiring, compiled-binary integration coverage, synchronized docs, and release changesets. This is package plumbing only; do not add or reinterpret NIP-5D, NIP-5A, NAP, manifest, or runtime protocol surface.
</objective>

<interfaces>
Existing contracts to preserve and adapt:

- `packages/cli/src/cli.ts` dispatches `create` and `skills` with `parsed.rest`; its outer `main(argv): Promise<number>` prints a thrown error and returns `1`.
- `packages/boilerplate/src/index.ts` already exports `main(argv = process.argv.slice(2)): Promise<void>` and guards direct execution by comparing the resolved process entrypoint to `fileURLToPath(import.meta.url)`. Its executable wrapper prefixes failures with `@napplet/boilerplate:` and sets exit status `1`.
- `packages/skills/src/cli.ts` currently parses `list`, `print`, and `install`, returns `0`, `1`, or `2`, writes through `console`, and ends with unconditional `process.exit(...)`; importing it is therefore unsafe.
- `packages/skills/src/index.ts` discovers and reads `skills/*/SKILL.md` from the shipped package directory at runtime. Deno's default `compile` mode embeds the resolved npm/workspace dependency tree; the integration test must prove these non-code assets are present instead of assuming it.
</interfaces>
